# Managed Slack identity binding

This slice links a verified native workspace member to a Slack user under one active managed installation. It does not authorize reading a channel or thread, a provider, billing, execution, output publication, or approval. Execution is never automatic. An explicitly granted, self-authored Slack app mention in one exact thread can become a private native draft; it does not supply source access or execution authority.

The native member starts a short-lived challenge for the exact installation. A cryptographically random one-use secret is returned once; only its hash is stored. The member submits it as `/shiba-link <secret>` in Slack. The managed ingress validates the signed raw request and active app/team before recording its Slack user ID. The same current verified native session must then review and explicitly confirm that exact ID in Shiba. The Slack user must first accept a signed interactive prompt naming the verified native account, native UUID and workspace; a pasted challenge alone cannot link the accounts. Slack display names, installers, room owners, and bot visibility are never identity proof. Binding is unique to an active installation and native account and can be revoked. A changed installation generation or native membership permanently revokes pending and active bindings. State reads recheck the native account and installation; execution consumers must additionally implement their own full source and action fences.

The app operator must explicitly enable interactivity at `/api/slack/interact`, configure the `/shiba-link` slash command to use the existing `/api/slack/command` endpoint and include Slack's `commands` scope in a separately reviewed managed installation. Slash commands cannot be invoked in threads. The challenge is sensitive: do not paste it into an ordinary message, URL, log, or another person's command. The operator must verify request-body logging redaction before use; the application does not prove that infrastructure logs are redacted. No Slack app configuration or installation is changed by this code. See Slack's [slash command guide](https://docs.slack.dev/interactivity/implementing-slash-commands), [account binding guide](https://docs.slack.dev/authentication/binding-accounts-across-services), and [request signature guide](https://docs.slack.dev/authentication/verifying-requests-from-slack).

An explicitly selected binding, channel and thread permits future self-authored app mentions for 24 hours. Drafts are private to the bound native account and require current native membership and installation. Duplicate event/message identities cannot create another draft. Received signed edits and deletes invalidate pending drafts, including when the change arrives before the original. The operator must configure the relevant app mention and message-change subscriptions and scopes: the code cannot establish that Slack delivered every edit or delete, so a draft is not proof that the original message still exists or that the author currently belongs to the channel. Adoption copies the text once into a native composer; later Slack edits cannot retract already copied text. The human must review it as an untrusted author statement, select an authorized target and personal provider, and use the existing approval gate. A lost adoption response is not retried automatically. No Slack history or thread contents are imported.

The native coworker panel can now submit a retained self-authored statement into the existing personal execution path. The human selects an accessible room, active employee and current owned local Claude/Codex grant, then reviews an expiring server-authored preview. That preview freezes the exact statement, room audience, employee version and full nonsecret personal grant. Sharing the statement and results with that room requires an explicit consent. Submission creates a pending approval; a separate current native human decision is still required before any child or mailbox work starts. The room handoff shows approval, execution status and results. Prince selected private Slack status with full results in the authorized Shiba room. Each native user must separately opt in to the exact verified Slack recipient and thread in the reviewed preview. Copying a draft or submitting without that opt-in creates no notice permission. Task text, results, diffs, files and artifact links are never included in these notices.

A purpose-specific Worker HMAC binds the actual forwarded task/employee/grant body to the native account, workspace, session, preview and expiry. A one-use D1 transition consumes it before room reservation. Public requests cannot create reserved `scx_` handoffs. The actual canonical employee-prefixed task, personal snapshot and approval identity are checked again at queue, approval, child dispatch and local claim. Changed source, room audience, current employee version, identity, installation, intake or personal grant blocks later use. Revoked source reads retain only minimal owner/session-fenced submission metadata, without the statement or preview. Unknown queue outcomes and legacy unbound receipts cannot authorize a replay. An abandoned submission becomes `unknown` after expiry; it is not relaunched.

This is an explicit copy-and-execute contract for the author's own retained statement. It does not import Slack history, establish current private-channel membership or prove delivery of every edit/delete. A signed event supplies neither native credentials nor billing authority. Execution is restricted to the explicitly selected person's paired local Claude/Codex account and approved public repository, without deployment-provider fallback, setup scripts, app tools or PR publication. Revocation is rechecked immediately before claim, but D1 and the mailbox Durable Object are separate stores: no atomic cross-store revocation or cancellation/refund of already running CLI work is promised. Native fixtures and fake signed requests do not establish an installed Slack/provider integration. See the [V2 acceptance report](verification/slack-coworker-v2-20261105.md).

The local store admits at most three live link attempts, 16 active intake grants and 100 pending drafts per native account, with 1,000 retained challenge, grant and draft records each. Security tombstones are capped at 10,000 per Slack team; reaching that limit revokes active intake grants rather than accepting untracked late events. There is no automatic history recycling in this slice. Capacity exhaustion requires an operator-reviewed maintenance approach; it never causes an automatic retry or grants broader access.


## Separately consented private status

Private notices are default off. An operator must configure the existing managed installation and encrypted keyring, then explicitly set `SLACK_COWORKER_PRIVATE_STATUS_ENABLED=true`. The existing five-minute Worker cron observes at most 20 due grants per tick. The human reviews the exact app/team/channel/thread/Slack user, installation digest, expiry and six-notice limit before choosing the separate unchecked notice consent. The notice lease cannot outlive the source intake, personal grant, installation or 24 hours. Enabling the operator flag alone does not create a user grant.

The Worker verifies the retained approval/run and current source, personal grant, room audience, current profile and installation. It checks the token identity with fixed `auth.test` and uses only fixed `chat.postEphemeral` to the reviewed recipient. Native pending review, rejection, approved waiting, running, completion and stopped states use fixed content-free text and an opaque task suffix. No shared message, direct-message fallback, channel join or alternate recipient is attempted. These status permissions never approve or start CLI work.

A durable per-status reservation caps each grant at six attempts, with at least five minutes between observations. Concurrent ticks cannot repeat the same status. In-flight or unconfirmed sends become `unknown` and are never automatically retried. A successful Slack receipt means API acceptance, not confirmed user delivery. Slack documents that [ephemeral messages are nonpersistent and delivery is not guaranteed](https://docs.slack.dev/reference/methods/chat.postEphemeral/); an active channel membership and Slack session are required. Short-lived states may be coalesced. The authorized Shiba room remains the durable source of status and full results.

`POST /api/slack/coworker/drafts/status/revoke` accepts only an owned preview ID, explicit review and a current native session. Stopping notices does not cancel the task. Minimal owner-fenced notice state remains inspectable after the private-status flag, managed-installation flag or keyring is disabled. These metadata-only exceptions never expose the statement or permit new work. Revocation is checked immediately before the send; the database and Slack are separate systems, so an already in-flight message cannot be withdrawn by this contract. No live Slack sends or deployment were performed during fixture verification.
