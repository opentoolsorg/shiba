# Managed Slack identity binding

This slice links a verified native workspace member to a Slack user under one active managed installation. It does not authorize reading a channel or thread, a provider, billing, execution, output publication, or approval. Execution is never automatic. An explicitly granted, self-authored Slack app mention in one exact thread can become a private native draft; it does not supply source access or execution authority.

The native member starts a short-lived challenge for the exact installation. A cryptographically random one-use secret is returned once; only its hash is stored. The member submits it as `/shiba-link <secret>` in Slack. The managed ingress validates the signed raw request and active app/team before recording its Slack user ID. The same current verified native session must then review and explicitly confirm that exact ID in Shiba. The Slack user must first accept a signed interactive prompt naming the verified native account, native UUID and workspace; a pasted challenge alone cannot link the accounts. Slack display names, installers, room owners, and bot visibility are never identity proof. Binding is unique to an active installation and native account and can be revoked. A changed installation generation or native membership permanently revokes pending and active bindings. State reads recheck the native account and installation; execution consumers must additionally implement their own full source and action fences.

The app operator must explicitly enable interactivity at `/api/slack/interact`, configure the `/shiba-link` slash command to use the existing `/api/slack/command` endpoint and include Slack's `commands` scope in a separately reviewed managed installation. Slash commands cannot be invoked in threads. The challenge is sensitive: do not paste it into an ordinary message, URL, log, or another person's command. The operator must verify request-body logging redaction before use; the application does not prove that infrastructure logs are redacted. No Slack app configuration or installation is changed by this code. See Slack's [slash command guide](https://docs.slack.dev/interactivity/implementing-slash-commands), [account binding guide](https://docs.slack.dev/authentication/binding-accounts-across-services), and [request signature guide](https://docs.slack.dev/authentication/verifying-requests-from-slack).

An explicitly selected binding, channel and thread permits future self-authored app mentions for 24 hours. Drafts are private to the bound native account and require current native membership and installation. Duplicate event/message identities cannot create another draft. Received signed edits and deletes invalidate pending drafts, including when the change arrives before the original. The operator must configure the relevant app mention and message-change subscriptions and scopes: the code cannot establish that Slack delivered every edit or delete, so a draft is not proof that the original message still exists or that the author currently belongs to the channel. Adoption copies the text once into a native composer; later Slack edits cannot retract already copied text. The human must review it as an untrusted author statement, select an authorized target and personal provider, and use the existing approval gate. A lost adoption response is not retried automatically. No Slack history or thread contents are imported.

A Slack-backed execution queue still needs proof of the native member's current access to the source including private-thread membership, delivery/reconciliation guarantees, and a source fence carried through the existing frozen review and execution gate. The personal execution path currently demands a native dashboard session, current personal provider grant and a collaboration handoff. A signed bot event cannot supply those credentials or a dashboard voucher. It also cannot authorize use of deployment billing. Native fixtures and fake signed requests do not establish a live Slack installation or current Slack membership.

The local store admits at most three live link attempts, 16 active intake grants and 100 pending drafts per native account, with 1,000 retained challenge, grant and draft records each. Security tombstones are capped at 10,000 per Slack team; reaching that limit revokes active intake grants rather than accepting untracked late events. There is no automatic history recycling in this slice. Capacity exhaustion requires an operator-reviewed maintenance approach; it never causes an automatic retry or grants broader access.
