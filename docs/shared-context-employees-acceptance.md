## Architecture and authority

The implementation extends the existing D1 collaboration room, membership, message and handoff store. It does not create another team registry or widen the private Memory DO. The deployment currently uses the `self-hosted/default` collaboration scope with explicit room members. Built-in Better Auth still has a single bootstrap-owner signup contract; deployed teams need configured Access identities or separately provisioned accounts. Viktor-style invite administration, groups and multiple Slack installations are not implemented by this change.

## Slack continuity and approvals

An observed or signed Slack event does not prove that a dashboard room owner may disclose it. The existing `SLACK_CANVAS_OWNERS` configuration now also binds source import to the exact team/channel, configured origin owner and approved audience. Empty or malformed policy disables discovery, linking, import and delivery. Existing and revoked links protect retained source material. Membership insertion and source linking use atomic SQL audience fences, so either ordering of a concurrent invite/link cannot widen the audience.

Incoming events retain their Slack actor, event, thread and message identities. Slack actors are not guessed to be dashboard users and do not receive room-read or approval authority. Mapping a thread does not silently authorize web-room data to be posted back to Slack. Outbound delivery retains a separate frozen human decision and one-shot receipt/unknown-outcome handling.

Existing exact-thread durable buffering, attributed next-turn decisions, persona/status messages, signature/timestamp verification, first-use action decisions and completion routing remain. The new shared-note workflow uses explicit selection and approved handoff context. It does not passively merge all channels, DMs, private memories or connector permissions.

Native employee app approvals now apply the same person-level checks to preview and decision. Private integration actions require the canonical connection owner; an employee/actor label or deployment organization is insufficient. Other actions require the owned execution session or an explicit operator approver policy. A first human decision atomically records owner proof, and dispatch rechecks current profile, session, grants, connection and policy. Nineteen independent ownership regressions cover unrelated users, account mismatch, replay, legacy missing proof and revoked authority. Private Slack/Telegram/Discord decisions cannot infer canonical dashboard connection ownership and fail closed until an explicit verified mapping exists. Shared chat decisions retain their current signed-channel allowlist checks. Live installed Slack approval, delivery and provider execution remain unverified.

Templates are optional instructions and draft deliverable contracts. They do not connect accounts, install MCP servers/skills, assign policy roles, grant data access or start execution. HR and finance templates require reviewed drafts and explicitly exclude autonomous personnel decisions, money movement and filings.

Validated `roleTemplateId` provenance survives profile creation, editing, renamed labels/slugs, saved drafts and explicit pack imports. Required deliverables survive pack round trips. Occupational roles are separate from authorization roles such as owner/admin/member.

Onboarding exposes searchable roles, custom choices, skip/resume and explicit deferred setup for Providers, apps/MCP, skills and employee permissions. Existing saved drafts, version checks, private source pins and return-to-Work behavior remain. Preparing a starter draft requires an explicit supported Claude Code, Codex or OpenCode choice; it does not queue or approve a run. Configuration/checklist progress is not presented as successful model execution.

## Apps, MCP and skills

The catalog is a discovery surface. Its thirty-nine static entries include nine implemented product paths and thirty catalog-only entries; these counts do not mean connected accounts or usable employee tools. All six existing curated vendor MCP presets are visible, including previously hidden Figma, PostHog and Atlassian. Role recommendations link to existing setup and permission views without inventing integrations.

Search/domain/role filtering also applies after provider rows are merged. Deployment availability is distinct from configured and healthy state. Draft, unreviewed, errored or disabled MCP records cannot be represented as connected execution. Employee app setup exposes the existing registered integration search/execute capabilities with owned connection/resource/version checks; ambiguous or stale account selection fails closed. The upstream provider exposes no credential generation, so replacing vendor credentials behind an unchanged connection ID cannot be independently detected; no live reconnect guarantee is claimed.

Enabled employee Work turns can discover and read authorized extension skills. Reads revalidate owner/workspace, lifecycle and expected version; connected-app reads resolve the owned session again each call. Chat stays tool-free, and Slack gets no guessed personal scope. These read-only instructions grant no tool authority. Reviewed managed skill attachments also reach employee app Work through latest-human metadata, with a maximum of five unique exact versions. The actual orchestrator resolves the owned employee/session/workspace, supplies reviewed guidance to the model and retains exact pins in draft provenance. Native tool dispatch rechecks that binding after asynchronous discovery and immediately before the guarded provider effect; revoked or changed skills fail closed. Existing sandbox approval pins retain their separate gate. Pack skill/plugin metadata is not represented as installed or active merely because a role was selected.

A final narrow managed-skill integration assignment closes the selected-pin handoff between the composer and employee draft tools. It verified presence, attributed messages, explicit notes/selection, an authenticated outsider's denial, reload and removal clearing cached data. Known console warnings are retained. The source hash manifest predates the final small capacity/notification fixes; those have deterministic regression coverage.
