# Standing Slack delivery for Stripe captures

Stripe scheduled reads and future Slack delivery are separate authorities. This optional lane starts no Stripe reads, payments, models or messages during setup. A verified native source owner must select a current completed private receipt and a managed room-linked Slack thread, prepare an exact grant, then explicitly consent to disclosure to all current and future people who can read that Slack channel and thread. A different configured native manager who is a current room reader must independently review and approve the same sample and grant digest. Both decisions require their own verified native cookie session and final database session and membership checks; a bot, scheduler, display name or OAuth installation is not a human approval.

The grant pins the source owner UUID and membership revision, source grant revision, contract and executor digests, account, restricted-key fingerprint, fixed read selection and expiry. It also pins the managed Slack app/team, channel/thread, installation generation, version and token revision, room audience, policy, maximum one to ten sends and expiry. Its review expires in 15 minutes; delivery expires no later than the source or Slack token lease and at most 28 days. The sample is private and must remain current for disclosure and approval. An expired sample is no longer shown; it is not perpetual access to historical output.

The `stripe-qualified-rows.v1` renderer deterministically includes the exact capture identifiers and digests, account/mode, capture time, selected window, every captured projected row with currency minor units, and explicit bounded-capture, unknown dataset completeness and unverified business success. It makes no payment, revenue, MRR, churn or full-ledger reconciliation claim. The text is escaped and blocked above 3,500 UTF-8 bytes; it is never silently truncated. The complete original receipt remains private. This fixed policy and its generated renderer source digest are separately disclosed and are not an upgrade of an OAuth report grant. The manifest check covers the source adapter and shared Slack escaping implementation; regenerating a changed digest invalidates old standing grants and requires a fresh human review.

Only completed receipts created strictly after the manager's approval can be delivered. No source history is fetched and the scheduler does not retry an old receipt. One atomic reservation spends a send slot and inserts a per-occurrence record into the existing shared `founder_automatic_slack_deliveries` ledger. A prior sending or unknown result for the destination blocks Stripe and OAuth families across replacement grants and installation generations. An orphaned lease becomes unknown; it is never automatically retried or refunded. Known rejection and preflight failure also block future sends. Local disable or source revocation cannot retract Slack messages that were already delivered.

Immediately before one fixed Slack POST, the Worker revalidates the exact source report bytes/digest and owner, approved family/destination, audience, installation, human authority, reservation and expiry in one final D1 fence, followed by a synchronous deadline check. A concurrent revocation or changed source fails closed. The sender uses a fixed endpoint with manual redirects and no channel discovery, mentions, unfurls or broadcasts. No native Slack identity, provider/billing or model authority is inferred.

The original source owner can open a completed private report and select **Review future Stripe Slack delivery**. The panel displays the exact sample, family and wider audience before a separate disclosure. The manager can open the shared nonsecret delivery grant ID in the workspace's separate Stripe Slack review panel and approve only after reviewing it. There is no API or UI operation to auto-approve. The API is `/api/founder-stripe-slack`, with explicit prepare, exact grant read and disclose/approve/pause/revoke actions. Append-only migration `0031_founder_slack_sources.sql` supplies the separate grant table; the old shared delivery ledger remains the cross-family latch.

Local verification uses SQLite and fake bot verification/Slack transport only. It does not establish a live Stripe account, Slack installation, Slack channel membership, provider acceptance, deployment, billing or message delivery. Live acceptance still requires separately authorized operator configuration, native identities and an approved non-production setup.
