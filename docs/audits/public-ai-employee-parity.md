## Method and evidence limits

I used REA's published investigation method as an evidence discipline: ask one feature question at a time, inspect the visible page and behavior, record what was directly observed, and separate conclusions from evidence. REA's browser guide describes starting observation before performing one action, then recording the request, response, initiator, and relevant loaded script. This workspace had no authorized authenticated browser session for the Overlay workspace and no configured REA MCP/browser endpoint. I did **not** install REA, run its downloaded analyzer, access a logged-in workspace, or capture private network traffic. The inspected page content below comes from current public web page retrieval and search-indexed official pages; vendor copy is identified as a claim rather than runtime proof.

REA method references:

- [Official REA README: How REA works and evidence limits](https://github.com/morluto/rea#how-rea-works)
- [Official REA browser and network guide](https://rea.tools/guides/browser/)

## Prioritized end-to-end acceptance scenarios

These scenarios translate the public evidence into Shiba-specific checks without copying product branding or asserting unobserved reference internals. They are acceptance targets, not a declaration that every flow already passes.

### REA-informed state-transition journey

The table below is a practical target for the complete employee workflow. REA's
browser method is to capture one deliberate action at a time and connect the
visible result to the requests and evidence caused by that action. The public
Overlay homepage mockup (O2) shows the broad Work → employee conversation →
computer shape, and Viktor's public copy (V1) claims chat delegation, tools,
review gates and returned work. Neither source exposes the authenticated
onboarding path or backend state. Therefore, the rows below are **Shiba
acceptance design**, with competitor evidence called out separately; they are
not a claim that competitor interactions were replayed or that the products
have identical screens.

| Step / transition | Entry condition and action | Expected exit condition (Shiba acceptance) | Interrupt, error and repeat cases | Evidence required; reference status |
| --- | --- | --- | --- | --- |
| 0. Public entry → sign-in/onboarding | Open a fresh Shiba deployment as a new identity and begin setup. | User sees setup progress and the next required step; account/identity is canonical and setup completion is persisted. | Reload mid-step, back/forward, repeat submit, expired auth, or existing user re-entry must resume safely without duplicate workspace/account creation. | UI state plus persisted onboarding record and identity response before/after reload. Competitor: **access-blocked**; Viktor's install-to-chat is a published claim (V1), Overlay's public page has sign-in CTA but no inspectable onboarding (O2). |
| 1. Onboarding → workspace | Finish the required setup and enter the selected personal/team workspace. | Workspace identity, membership, available capabilities, and empty/loading/error state are explicit; refresh restores the same authorized workspace. | Missing required integration, stale membership, network failure, or a second account/workspace switch must fail visibly and never carry prior workspace data across identity. | Authenticated workspace ID/membership response plus negative cross-workspace read check. Competitor: **inferred** from Overlay's multiplayer/workspace positioning (O2/O3), not directly observed as a flow. |
| 2. Workspace → employee | Create a named employee by choosing only available role/runtime/model settings and saving instructions. | Employee appears in the roster with durable ID and version; detail/reopen reflects server-saved values and readiness accurately. | Required fields invalid, provider unavailable, double-save, stale edit, or interrupted save show an error/retry path; duplicate retry does not create unintended employees. | Before/after API response, stored profile revision, and roster after reload. Competitor: agent roster is a public static mockup (O2); create/edit UI is **blocked**. |
| 3. Employee → chat or work task | Open that employee's conversation; submit a normal chat turn or explicitly start a task with a goal and expected output. | Chat turn is associated with the selected employee/session; task has a durable ID, chosen mode, frozen input/config version and visible status. The interface makes chat and work distinct. | Refresh during send, double-send, websocket loss, switch employee mid-response, empty prompt, or provider error must not attach the reply to the wrong session or report an unsaved task as started. | Session/task IDs, request payload and persisted transcript/task state before/after reload. Competitor: Grok's logged-out prompt shell (G1) and Overlay Chat/Work inventory (O3) are observations/claims; send behavior is unverified. |
| 4. Task → tool readiness | Inspect required connectors/tools; show server-truth connection state and scopes before planning an external action. | Available tools, access scope and read/write capability are explicit; the employee can produce a plan or a clear blocked result if a required tool is absent. | Disconnected, expired/revoked, timeout, denied scope, malformed result and duplicate read are visible states; never substitute a seeded green badge or fabricated result. | Connector status from backend, scope record and tool-call receipt/error. Competitor: tools are advertised (V1/O2/O3); live connection state is **not observed**. |
| 5. Tool plan → approval | For a consequential write, show the exact target, effect and frozen arguments and request a human decision. | Approval is bound to the task/config/tool-argument digest; no side effect or sandbox begins while pending. Reject ends safely; edits invalidate old approval. | Repeat approval click is idempotent; stale approval, changed arguments, expired identity or rejection cannot authorize a changed action. | Approval row/digest, tool invocation state, and deterministic adapter assertion of zero writes before approval. Competitor: Viktor says sensitive/irreversible actions wait for approval (V1); its UI is not observed. Overlay's public mockup labels a task “Needs you” (O2), but its approval interaction is unverified. |
| 6. Approved → executing | Approve the frozen plan and start through the configured deterministic test adapter or explicitly configured runtime. | Run links to approval, task, employee/config revision and tool receipts; progress states advance and cancellation fences the run. | Worker restart, tool timeout, ambiguous response, sandbox loss, cancellation and retry preserve lineage; unknown external outcomes require reconciliation before retry. | Run/approval lineage, event history, mock-tool invocation count, and cancellation/retry result. Competitor: O2's mockup reports elapsed time and tool count but this does not prove live execution; runtime internals are **inferred/unknown**. |
| 7. Executing → result/review | Finish work and return artifact(s), explanation, sources and checks to the same task conversation. | Result has retrievable version/digest and provenance; verification is pass/fail/partial/blocked, and task is complete only when required criteria pass and review is satisfied. | Partial output, failed check, lost download, duplicate completion event, refresh, or reviewer rejection must preserve prior version and show a truthful state; rerun creates lineage rather than overwriting silently. | Artifact fetch after reload, digest/source records, verification result and explicit terminal state. Competitor: sample report/venue shortlist is marketing-demo content (V1/O2), not observed generated output. |
| 8. Result → follow-up or stop | User asks a follow-up, retries a failed step, or converts a repeatable task into a schedule. | Follow-up references prior context/result; schedule persists owner, timezone, scope, approval policy, next occurrence and pause/delete control. | Repeated schedule creation, disabled integration, retry after ambiguous action, pause during run, or cancel must not duplicate writes or claim completion. | Persisted follow-up lineage/schedule and deterministic next-run/stop behavior. Competitor: recurring work/Automations are advertised (V1/O2/O3); schedule creation and execution are **not observed**. |

**End-to-end acceptance rule:** execute the complete 0→8 journey with a local
deterministic adapter, then repeat the interruption/recovery cases at each
durable boundary. Keep a single evidence bundle with request/response traces,
persisted IDs and version/digest checks, tool-call receipts, UI-visible state
and test output. Add a real connector/model run only when an authorized test
account is configured; label that result separately from local acceptance.

### P0 — delegation and trust contract

1. **P0-1 — Start in chat and choose work intentionally.** Open a new Shiba session, enter an ordinary question and a delegated task separately, see the corresponding response/work state, select an available employee/provider, and recover both threads after reload. If no provider is configured, show a useful blocked/error state.
2. **P0-2 — Frozen approval through outcome.** Submit an approved coding or artifact task. Assert it creates an approval record only, with no sandbox before approval. Approve the exact frozen task/config; execute deterministic local work; retain run status, verification output and deliverables; reload and confirm the same content digest and history. Reject/cancel must leave no executing task.
3. **P0-3 — Self-hosted memory lifecycle.** Create/update/search/delete a fact through the UI. Restart the local app/storage service and verify persistence or documented recoverable failure. Verify identity and workspace boundaries with two principals; no fact can leak or be found cross-scope.
4. **P0-4 — Connector truthful state.** With a local deterministic adapter, show disconnected, connected, expired/revoked and error states. Never show a live green connection based on seeded/demo data. A real write remains blocked until explicit approval and a configured test target is used; store action result/unknown outcome and prevent blind duplicate retries.
5. **P0-5 — Self-hosted bootstrap and recovery.** Install/configure in a clean local environment, initialize migrations, use the deployment's own persistence, create an account and first employee, execute a deterministic safe task, backup/restore state, and verify that no secret is rendered, logged, or passed to sandbox code.
6. **P0-6 — Repository-free scheduled work.** Create an interval or calendar-based task without inventing a GitHub repository. Persist owner, timezone, scope, employee/config version, approval policy, next-run time and stop control. Run deterministically, retain an artifact, pause/resume, and prove retry/cancel behavior.

### P1 — workspace and employee quality

7. **P1-1 — Employee lifecycle and reusable skill.** Create a named employee with role/instructions/provider; version and review a skill; activate and pin it; start a conversation; prove profile/skill versions and defaults persist through refresh and that changing the skill does not rewrite prior approved input.
8. **P1-2 — Shared room and handoff.** Owner creates a room, adds a second authorized member, assigns/hands off a child task, sees progress and a durable returned artifact. Reload both principals; unauthorized room/task/artifact access is denied. A failed child remains failed/blocked; parent is not marked complete.
9. **P1-3 — Useful chat interaction.** Keyboard-only and small-screen run through prompt composition, attachment/context selection, available model selection, send/stream, stop/cancel, error recovery and history. Distinguish chat from task execution; make slash-command shortcuts discoverable only if implemented.
10. **P1-4 — Evidence-backed external research.** Research a public topic using allowed sources, retain URL/access time and claim-to-source links, label inference and unavailable pages, and verify claims against retrieved evidence. No account-only page is represented as read.

### P2 — broader workbench parity

11. **P2-1 — Project knowledge and generated outputs.** Create a project, upload test documents, extract/index/search with access controls, create an editable note, generate an output with source provenance, and reopen/version/download it after reload.
12. **P2-2 — Persistent browser/computer.** Reconnect to a scoped authorized runtime, preserve only intended work state, validate no credential leakage, record tool actions and cleanup behavior, and ensure browser/computer permissions inherit from the approved plan.
13. **P2-3 — Usage and model controls.** Change an available model for one task, show provider availability and actual recorded usage/cost, compare after reload, and prove failed/unconfigured providers do not report invented usage or success.

## Update rule

Repeat this audit when a public reference UI materially changes. Keep public page observations, vendor claims, Shiba code evidence, local execution, and live-service acceptance in separate rows/statuses. A URL returning a login screen, a passing unit test, a source file, or a marketing statement alone cannot change a blocked/not-verified status to PASS.
