## Common acceptance boundary

1. User, workspace and membership authority come from verified server identity. Occupational employee roles are recommendations, not owner/admin privileges. Private account credentials and owner memory remain private.
2. A human approves the exact frozen action, account/billing lane, target, versions, source context and expiry. A model, child, schedule or automation cannot approve itself. A connection or pairing is not an execution approval.
3. Recheck current membership, owner, grant, consent/account generation, source audience, profile version and original absolute approval deadline after awaited discovery/preflight and immediately before the effect. Use atomic conditional claims where state permits it. The prior final-D1-read expiry regression must not return through these new paths.
4. Unknown external outcomes retain one-shot claims and prohibit automatic relaunch or repeated writes. Cancellation before dispatch prevents the call. Neither revocation nor cancellation promises retraction of an already accepted remote effect.
5. Presence of operator credentials is configuration, not funding consent. There is no implicit Workers AI, TypeSafe, distillation, review, follow-up, default connection, cloud runtime or deployment machine fallback in a personal execution lane.
6. Backend adapters, credentials, hashing/signing and policy stay server-side. Only browser-safe schemas and wire contracts belong in `@shiba/shared`. Existing monorepo dependency directions, append-only migrations and mirrored deployment declarations remain in force.
7. Local fixtures establish their named code boundaries. Real provider/account entitlement, quota, vendor permissions, installed Slack and deployed Cloudflare remain separate acceptance. A CLI status receipt is not an inference or subscription entitlement test.

## Personal execution review requirements

The [existing personal execution assessment](../personal-team-execution-contract.md) is the governing starting point. At baseline, model connections are deployment-owned, legacy pairing does not prove a human owner and existing daemon setup can inherit local keys/copy both provider logins. Those are operator paths; they cannot become personal by a client-supplied owner field or room membership.

The proposed frozen grant includes version, grant ID/revision, immutable owner account ID, canonical actor email, workspace/membership version, machine/revision, harness, billing mode, account fingerprint, auth version, public repository, expiry and `allowedPhases: ["local_repository_task"]`. The claim must additionally bind the exact approval ID, original absolute approval expiry, input hash, execution owner, handoff and selected context digest. A missing claim proof must deny execution.

The local receipt contains a version, harness, native-subscription mode, SHA-256 fingerprint of nonsecret local account identifiers, a version for the exact selected auth material and CLI version, probe method and time. Server-observed freshness is bounded at 75 seconds. The implementation owner verified non-inference Claude auth status and Codex `account/read` with token refresh disabled against official contracts. The narrow adapter supports file-backed Claude native login on Linux from CLI 2.1.268 and file-backed Codex ChatGPT login on supported non-Windows machines from CLI 0.157.1. API keys, external providers/tokens, keychain-only or missing proof remain unsupported. No raw auth payload or token may reach the Worker, room, model or logs. A valid receipt is local CLI-state evidence, not proof of live entitlement, every managed host policy or quota. See [daemon support and limits](../personal-local-daemon.md).

Pairing requires an explicit local CLI and inspected account fingerprint in the request before the server generates a complete personal command. The human inspects the account locally first; the supplied fingerprint is configuration intent, not server-side provider proof. Grant creation still requires a fresh receipt from that exact owned machine. There is no automatic account, model or grant selection.

Required negative and integrated tests:

| Boundary | Minimum proof |
| :--- | :--- |
| Pairing/owner | Two verified humans and machines; reject forged/replayed/expired nonce, changed owner, legacy/unowned adoption, cross-workspace pairing and another actor's list/readiness/revoke. |
| Claims | Personal machines cannot claim deployment or another human's pending work, including unpinned work. Operator machines cannot claim personal work. Reject stale grant/account/membership revisions and replayed claims. |
| Account selection | Reject API-key/other-provider/cloud fallback, account drift, unsupported or missing probe, expired login and offline machine. Compare the receipt to the auth material actually used in the fresh run home. Do not copy both provider accounts. |
| Funding | Instrument coordinator, specialist, TypeSafe, distillation, chained review, setup and follow-up paths, including startup/reclaim/recovery. Forbidden phases make zero calls even when operator credentials are configured. |
| Approval | No execution before a named permitted human approves exact machine/account/repo/context/grant/versions/expiry. Reject autonomous approvals, changed profiles/sources, final-read expiry and revoked membership. |
| Retry/cancel | Lost claim response, duplicate delivery, cancellation and restart cannot launch a second CLI or move to a different machine. Uncertain execution stays unknown until reviewed. |
| Public repository | Prove public access anonymously. Do not borrow operator GitHub credentials, inherited local token variables or credential helpers to make a private target appear public. |
| Results | Two members plus a third/removed user prove current source-authorized task, transcript, artifact and cached-output access. Sharing a result does not share credentials, account metadata or private parent history. |

Native local execution runs as the human's operating system user. A fresh `HOME` is credential selection hygiene, not OS isolation against host file access. The UI/approval must not describe it as a tenant sandbox. Real account execution remains unavailable until the contract and authorized environment are verified.

## Personal frontend implementation and review boundary

The frontend now has a workspace/actor keyed personal client and setup panel, explicit local CLI/fingerprint pairing, own computer/grant revocation, required account-use and hosting acknowledgments, exact model/public repository selection and bounded grant expiry. Pairing codes stay in component memory, clear on close/scope change/expiry and are never stored in browser storage. Creating a grant neither selects it nor queues work.

The room form remains in personal mode when a grant becomes stale or revoked; it disables submission instead of switching to deployment execution. It sends only `personalExecution: { grantId, expectedVersion }` plus the ordinary task/profile/context fields. Runtime, account, machine, harness, model and repository are resolved and frozen by the server, with no client snapshot/route overrides.

The actual pending room approval card validates and displays its frozen personal account fingerprint, native billing, machine/revision, grant/version/expiry, exact model/repository and host-access boundary before an explicit review checkbox and decision. Its visible lease ends at the earlier approval or grant deadline. The live selector cannot replace these frozen fields.

Own local CLI permission controls use explicit server capabilities and the complete source action hash, expiry and grant/machine revisions. Missing/incomplete/oversized review disables Allow. Each request is first-click guarded; an uncertain response is not automatically retried. Retained own-process Stop is separate from permission to execute. Backend projection was corrected to return a minimal stop-only record after grant revocation, without cached private events/diff/request details. Membership-removed reads remain denied, while the narrow owned Stop API retains its independent authority.

The final affected five frontend suites passed 85 tests, frontend typecheck passed, the 11 affected frontend source/test files passed ESLint, and `git diff --check` passed. The suites are `personal-execution-client.test.ts`, `PersonalExecutionSetup.test.tsx`, `PersonalExecutionControls.test.tsx`, `RoomApprovalReview.test.tsx` and `CollaborationView.test.tsx`. They cover explicit pairing/grant consent, no provider fallback, scoped late responses, stale selection, exact queue selector, frozen approval scope, partial/expired request denial, duplicate click, mismatched receipt and stop-only capability cases. A preexisting context-limit test failed once in a resource-constrained aggregate; it then passed unchanged in isolation and in the final 85-test gate. No timeout or assertion was weakened.

A separate delegate independently reviewed the personal frontend and reran the earlier 82 tests. Its two additional actual-component regressions proved that a delayed permission decision and delayed initial account/grant reads cannot leak old authority after an actor/workspace switch. ## Workspace-shared connector review requirements

A `w_` alias proves Shiba partitioning, not legal ownership of the remote vendor account or its organization. The UI must use workspace-shared wording unless actual vendor ownership is verified. A member's personal `u_` consent cannot be relabeled, copied or transferred into workspace scope.

The source owner accepted the safer issuer lifecycle after review: the original consenting manager's exact active role and membership version must hold at every connection, grant and dispatch check. Departure, demotion or revoke/regrant pauses use. A fresh manager must explicitly disconnect and complete new upstream consent; no creator replacement or automatic transfer is permitted. The frozen source owner reports this policy is enforced and covered by actual SQLite/route fixtures; final root review and integrated revision checks remain separate.

Pending consent must bind a short-lived server state to the same workspace alias, service, initiating manager and exact membership version. The consent fingerprint comes from trusted upstream responses; a client echo is a selector, never proof. Completion must re-read that exact alias and generation before atomic activation. Unknown or ambiguous revocation is not blindly repeated.

Required proof includes two workspaces, three users, personal-account non-discovery, stale popup completion, wrong service/alias/generation, issuer removal/demotion/regrant during awaits, grant/profile/resource revocation, exact approval expiry and cancellation immediately before the provider call. Assert no upstream execute on every denied case. Integrate the actual routes, registry and provider adapter with fixture HTTP, then keep authorized live OAuth/action acceptance separate.
