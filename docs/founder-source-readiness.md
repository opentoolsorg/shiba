# Founder recipe source readiness

Source-only audit of Shiba revision `51b351c32fa2f6e51434fddebd1320fdfdf4b18a` and OpenConnector commit [`d89dc9f24f5a057bb500272d7dbf333837c77c68`](https://github.com/oomol-lab/open-connector/tree/d89dc9f24f5a057bb500272d7dbf333837c77c68), the `v1.9.4` commit pinned by [the operator helper](../infra/openconnector.mjs). Selected static upstream files were fetched at that immutable revision and checked against Git blob hashes from the complete pinned tree. No dependencies were installed, upstream code executed, account inventory read, provider operation invoked or credential created.

The audit distinguishes a declared operation, its executor, compatible consent and a complete workflow. A source pin does not attest the revision actually deployed by an OpenConnector sibling. Source metadata and fixture success do not establish vendor account permissions, availability, complete pagination or live results.

## Six recipes and concrete source gaps

The [six founder entries](../packages/shared/src/founder-skill-library.ts) describe intended reports and setup suggestions. The implemented [connector-job contract](founder-connector-jobs.md) creates one fixed action occurrence, followed by explicit human request, review and execution. It does not join services, paginate a report, calculate financial metrics, generate ticket drafts or send Slack digests on its own.

[Shiba's adapter](../apps/backend/src/integrations/openconnector-provider.ts) requires an active configured nonvirtual account with `oauthAuthorizationId`, and derives its reviewed generation fingerprint from that authorization. It intentionally does not treat an API-key record as execution-ready. Supporting API keys needs an explicit server-owned credential-generation/provenance and rotation/revocation contract. Do not fabricate an OAuth identifier or copy a key into task arguments to make readiness pass.

### Google Ads secret/schema conflict

The pinned [provider definition](https://github.com/oomol-lab/open-connector/blob/d89dc9f24f5a057bb500272d7dbf333837c77c68/src/providers/googleads/definition.ts) marks `developerToken` as a secret OAuth client field. Its [executor](https://github.com/oomol-lab/open-connector/blob/d89dc9f24f5a057bb500272d7dbf333837c77c68/src/providers/googleads/executors.ts) can obtain that value from protected credential context. However, the [action schema helper](https://github.com/oomol-lab/open-connector/blob/d89dc9f24f5a057bb500272d7dbf333837c77c68/src/providers/googleads/actions.ts#L412) also requires it in action input, and [execution validates input first](https://github.com/oomol-lab/open-connector/blob/d89dc9f24f5a057bb500272d7dbf333837c77c68/src/core/execution.ts).

Omitting the input field is therefore not established as executable through this schema. Supplying it would expose credential material in frozen plans, approvals and possibly reports. Resolve the contradiction through an audited server-only wrapper or upstream schema correction that injects the stored secret after public input validation. Test that the token never appears in browser DTOs, arguments, model messages, receipts or logs. No such fix or live compatibility is established by this audit.

### A read label does not enforce read-only behavior

Linear's [`run_query` declaration](https://github.com/oomol-lab/open-connector/blob/d89dc9f24f5a057bb500272d7dbf333837c77c68/src/providers/linear/actions.ts#L382) has read metadata. Its [executor](https://github.com/oomol-lab/open-connector/blob/d89dc9f24f5a057bb500272d7dbf333837c77c68/src/providers/linear/executors.ts#L1160) forwards the supplied document to the GraphQL request function without enforcing a query-only document. The code does not prevent a mutation document; acceptance at the vendor still depends on the credential's actual privileges. This is a source-derived boundary finding, not a live mutation test.

Exclude arbitrary GraphQL, generic proxy/HTTP and other user-defined query surfaces from an unattended-read allowlist unless their complete syntax/operation selection is independently constrained. A method name, GET/POST distinction, requested scope or provider metadata label alone is insufficient. At the audited `51b351c` baseline, [Shiba's action contract](../apps/backend/src/integrations/contracts.ts) dropped upstream operation classification. The current continuation preserves that field as advisory metadata, without granting read-only authority or changing existing human action approvals.

## Safe reports from already completed explicit receipts

The smallest safe addition is a deterministic **private evidence report** from explicitly selected, already completed, requester-owned receipts. It should not invoke a model, reread vendor datasets, execute another action, make a payment, update a CRM, create tickets or publish to Slack. Label it as captured evidence, with no claim that it completes the recipe.

Required boundaries:

1. Resolve the native actor and workspace server-side. Require the original requester UUID and exact selected receipt IDs; managerial ability to review an approval does not grant its requester-private result audience. Reuse current source/consent/employee/grant checks and a final all-row fence. Independent report viewing/download must recheck those sources; a new artifact must not bypass their revocation or extend the source read lease.
2. Bind receipt status, input hash, result digest, action/connection generation, observation timestamps and source selection into the report revision. Completed receipt data is historical evidence, not current vendor state. Missing or revoked selected receipts fail the report instead of disappearing silently from the denominator. An authorized current-connection metadata check is distinct from a new data/action read; do not claim a network-free path if the existing read service performs one.
3. Treat every result and URL as untrusted data. Render escaped text/JSON, validate known schemas, and make credentials, pagination cursors, download URLs, personal email and customer identifiers subject to explicit minimization. A field named as a recommendation or approval is not executable authority. Keep the report private unless a separate reviewed share explicitly names its audience.
4. Preserve semantic errors and coverage. An HTTP/action completion receipt is not proof of a successful or complete business query. The pinned [Linear raw GraphQL path](https://github.com/oomol-lab/open-connector/blob/d89dc9f24f5a057bb500272d7dbf333837c77c68/src/providers/linear/executors.ts#L1498) can return errors as data. [HubSpot's MCP unwrapping](https://github.com/oomol-lab/open-connector/blob/d89dc9f24f5a057bb500272d7dbf333837c77c68/src/providers/hubspot/runtime.ts) parses first-text JSON without visibly preserving every MCP error marker. Unknown/failed/partial data cannot become an empty successful result or zero revenue.
5. **Assume legacy receipt completeness is unknown.** The reviewed [result sanitizer](../apps/backend/src/workspace-integration-actions.ts) silently limits arrays and objects to 100 entries and strings to 4,000 characters. Deeper content is marked, and oversized whole envelopes can be replaced, but ordinary per-field omissions are not all annotated. A retained response can still say no more pages after rows were removed locally. Do not infer complete totals from it. New captures need explicit raw count, retained count, omitted paths, pagination/coverage status and known semantic error state; old records cannot be retroactively certified.
6. Financial output must preserve units, currency, exact period, metric definition and coverage. Do not aggregate across currencies, interpret redaction as zero, equate a customer balance with revenue, or claim no reconciliation exceptions from a partial page. “Observed retained rows” and “coverage unknown” are honest labels; a company-wide MRR or churn claim requires complete verified source data and reviewed calculations.

## Decisions required before unattended reads

Credentials and the following product authorizations solve different problems. Adding account secrets does not supply these decisions:

| Decision/contract | Minimum explicit scope |
| :--- | :--- |
| Standing read authorization | Named native source owner and current consenting manager; exact workspace account/consent generation, resource IDs, employee/skill versions and trusted read operation/schema/executor revision. No inherited private memory or deployment-default identity. |
| Permitted dynamic inputs | Exact account/repository/team/file allowlists; fields and query grammar; relative-period policy versus fixed dates; bounded pagination and any allowed fan-out. No arbitrary endpoint, GraphQL document or credential argument. |
| Cadence and budget | Start/timezone/expiry, calls/pages/records/bytes/time per occurrence, daily totals, quota/rate-limit treatment, missed-run policy and unknown-outcome handling. No silent catch-up or unlimited retries. Worker and vendor usage remain separate from model funding. |
| Attribution and revocation | Whether a reviewed standing grant survives logout; which current account/membership/source checks every scheduled attempt must satisfy; immediate pause on removal, generation change or revoked sources. A scheduler may use a standing human grant, never approve its own new action. |
| Report definitions | Period/timezone, currencies, conversion/attribution rules, MRR/churn conventions, CRM join key and expected completeness. Define which facts can be shown when inputs are incomplete. |
| Destination | Requester-private dashboard by default. A Slack digest needs a separate exact team/channel/thread, recipient/audience policy, content/source rules and send authorization. Read consent is not send consent. |
| Deployment trust | Authenticated proof of the active sibling's reviewed revision and an audited action manifest. Pinned local source and provider labels do not attest the deployed executor. |

Until those contracts exist and are tested, preserve the current human prepare/review/execute boundary. A private evidence report can be useful without enabling standing reads or publication. Live service access, new credentials, installations, vendor consent, real email/Slack sends and model calls require their separately authorized setup and tests.
