# Multi-agent control plane upgrade

This change extends the control plane at baseline `be13d0b`. It preserves the existing execution target, approval, event log, room, and Slack contracts. The later November 3 specification controls conflicting requirements. Reference verification and license findings are in [the reference audit](control-plane-reference-audit.md).

## Workspace and artifacts

The API accepts a `workspaceTarget` of `github` or `ephemeral`. Intake normalizes it into the established frozen `executionTarget`, so workspace identity, template hints, and required outputs participate in approval hashing. An ephemeral workspace has no repository or publication permission. It initializes `/workspace/.shiba` and `/workspace/out` without a clone. Existing artifact workspace callers retain their required text deliverable contract.

Archive collection reads regular files beneath `out/` from a retained immutable Git commit. It rejects traversal, symlinks, unsupported file modes, inconsistent hashes, truncated transport, and excess size or count. Empty directories and zero-byte files are supported. ZIP creation is bounded to 64 files, 1 MiB per file, and 8 MiB total input. Compression runs in Worker memory before the bounded archive is uploaded through the R2 binding. This is not an unbounded streaming zipper.

Provision the private `shiba-artifacts` bucket through the mirrored Wrangler or Alchemy configuration. Set the Worker secret `ARTIFACT_SIGNING_KEY` to at least 32 bytes and configure the public HTTPS `WORKER_HOSTNAME`. Missing configuration fails before sandbox acquisition. The download URL is a seven day, scoped HMAC capability served by the Worker over private R2. It is not an S3 presigned URL and requires no S3 credentials. Anyone holding the capability may download that bundle until expiry. Owner, run, sandbox, content digest, size, and expiry are bound into the capability.

The image adds pinned DuckDB and Agent Reach tools. Provider egress remains narrowly allowed. Installing a research tool does not grant arbitrary network access. Templates are bounded format hints, rather than remote executable installers.

## Bounded specialists

The coordinator exposes `explore_codebase`, approval-gated `delegate_coding_task`, and `review_diff`. Explorer and Reviewer are SDK `AIChatAgent` facets exported from the Worker. Their signed envelopes contain only explicit file snapshots, goal, context, specification, or diff. They have no shell, parent transcript, approval tools, integration credentials, or external write tools. Explorer searches only the supplied snapshot. It does not fetch an arbitrary repository.

A turn permits three sequential read-only inspections with a 60 second deadline. The remaining budget is durable. SDK child concurrency is set to one. Child routes require a retained tool run and an allowed class; children refuse nested facets. Coding child requests require a fresh workspace and a new frozen human approval, with depth one and at most three direct children. Parent budget consent cannot approve a different child task.

Coding dispatch uses a domain-separated HMAC over both the approved input digest and a SHA-256 digest of the complete canonical execution envelope. Owner routing, role, runtime, workspace, model, sealed environment, and bounded dispatch lifetime cannot change under an existing seal. Provider and subscription credentials remain at Worker egress.

## External actions

Automation triggers queue pending human approvals. Autonomous identities cannot resolve approval decisions. A coding child cannot publish a pull request.

When a coordinator run requests publication, the executor stages its exact file snapshot and diff in private R2 and returns metadata only. Successful fenced completion creates a durable read-only Reviewer handoff. The Reviewer receives the complete bounded staged diff and frozen task. A validated report bound to the owner, run and staged SHA-256 is required before a distinct `pr_publish` approval is created. Failed, timed-out, truncated or oversized review input leaves the coding result retained and creates no publication approval. The review limit is 64,000 characters. Approving the initial run does not publish changes. The publication action binds owner, run, repository, base branch, sandbox, immutable object and digest. The approved action is claimed durably before GitHub access. Mutation requests are attempted once. An interrupted or uncertain action is reported as unknown and is never automatically repeated or compensated with a branch deletion.

The staged bytes and approval also bind the exact captured repository base commit. Publication rejects an advanced base branch before any write and creates the new tree and commit from that immutable revision, including if the branch advances during publication. Git replacement refs cannot redirect immutable collection. Completion and the pending review share one fenced durable write. The successful report and its pending human publication approval share another atomic write. A failed notification leaves the pending action discoverable. Publication success commits the PR receipt, binding and executed approval together before starting an optional approved PR review; restart can recover that handoff without repeating publication. Commit attribution uses the actual verified approving identity in an `Approved-by` trailer and does not invent a GitHub email.

Body-free structured child observations are appended to the coordinator history with stable IDs after fenced settlement. This does not run another model turn or resolve an SDK approval part. A failed history append can be recovered without rerunning the CLI or publishing again.

If the SDK state write throws after updating memory, the orchestrator resets through [Durable Object `abort`](https://developers.cloudflare.com/durable-objects/api/state/#abort); it refuses subsequent writes from that instance. Review posting also persists a claim before its external mutation. A lost or ambiguous review receipt becomes unknown and blocks automatic, lifecycle, and explicit retries until the repository can be inspected. A known GitHub validation rejection remains retryable.

## Live rooms

The authenticated session room accepts server-owned terminal, status, diff, and child frames through binding RPC. Browser messages cannot append these frames. Each accepted frame has a durable sequence and stable event ID. Reconnect resumes from a cursor and deduplicates accepted frames. Retention is bounded to 2,048 frames. Expired cursors, failed delivery, oversized output, and interrupted execution transport produce an explicit gap or uncertainty indicator.

The existing run progress and diff components now include an xterm terminal, viewer presence, live diffs, run children, and session specialists. Socket leases prevent one viewer from taking over another viewer's browser relay stream. Navigation clears output and replay cursors; late frames from a previous session are ignored. A room append has a deadline and a circuit breaker so a stalled viewer service cannot hold execution indefinitely.

Viewer labels come from independently authenticated identities. Normal dashboard rooms remain owner scoped. Explicit Slack canvas viewers can share the exact read-only run room through the policy below. Their tab markers are scoped to the authenticated identity, so reusing another viewer's tab nonce cannot impersonate that viewer's presence. Both WebSocket ingress paths overwrite the trusted actor header before attachment labels are assigned. Cursor coordinates are relative to the live panel, bounded between zero and one, limited to ten updates per second, and expire after fifteen seconds. The `client_presence` protocol carries typing and cursor updates. `prompt_input` remains deduplicated peer chat with server attribution and is labeled Peer chat in the transcript. It does not start a coordinator turn or rewrite approved execution input. Read-only Slack viewers cannot send peer chat or relay writes.

During execution, the bounded live diff previews tracked changes relative to the sandbox's current HEAD. Untracked files appear in the final collected diff after the harness settles. Final repository collection freezes both checkpoint commit IDs and reads the changed-file list, deletions, and verified blob bytes from those immutable snapshots. Later changes to HEAD, checkpoint refs, or files cannot alter the proposed publication. The publication also retains the original cloned GitHub base revision.

Browser reconnect and DO replay do not imply resumption of a lost CLI process. If harness transport is lost after output, the runtime reports uncertainty rather than replaying the whole command. Live Cloudflare container transport recovery still needs cloud acceptance.

## Slack

Lead, Explorer, Fixer, and Reviewer use distinct names and emoji with one configured bot token. Installations need `chat:write.customize`; existing installations may need to be reauthorized. The implementation does not claim multi-installation OAuth support or an `agent_view` status API. Progress updates edit a stable thread status message.

Slack run canvases require an explicit `SLACK_CANVAS_OWNERS` policy. Set a JSON array of at most 64 records with `teamId`, `channelId` and `ownerId`, where `ownerId` is the configured Cloudflare Access email that owns the frozen room. Each record may also contain `viewerIds`, an allowlist of at most 16 independently authenticated Access emails allowed to read only that channel's exact Slack canvases. Omitting `viewerIds` preserves owner-only access. Invalid emails, duplicate viewers and invalid or duplicate channel mappings fail closed. The default empty array disables this feature. Cloudflare Access and an existing `INTERNAL_SIGNING_KEY` of at least 32 characters are also required. Viewer grants do not change room ownership, allow access to the owner's dashboard sessions, or grant execution or approval permission. No email is inferred from a Slack user ID.

With that policy configured, the exact `/slack-canvas/` locator shows the retained pending task and target, then the matching run's read-only terminal and diff stream. There are no execution or approval controls on this view. Queue provenance is signed over the exact body, method, destination, Slack origin, and timestamp, and is retained with the approval. Reads and WebSocket reconnects require both that provenance and a currently allowed Access identity. Frozen owner, room identity and run approval must match. Revoked owners or viewers and missing retained proofs deny access. Without a configured live canvas, Open Shiba remains a dashboard home link. Existing collaboration Slack message links do not grant execution-room access. The policy is operator supplied; live Slack, Access and container streaming acceptance remain unverified.

Use `workspace:<id>` in a mention or slash command to request a repo-free task. Run approvals disclose requested publication; the separate publication card approves the frozen external action. Callbacks verify the Slack raw-body signature and timestamp, approver allowlist, known action ID, and thread workspace scope. Unauthorized clicks produce an ephemeral denial without mutating approvals or runs.

Verified incoming events are buffered directly with author, event ID, text and timestamp while a run is active. A separate signed internal request prevents callers from forging Slack authors. The queue is durable, bounded, deduplicated and claimed before processing. Settlement submits the complete attributed batch into the pinned SDK's durable coordinator decision queue. Explicit message, submission and idempotency IDs survive retries. Acknowledgment follows a matching durable submission receipt. Lead can answer a question, inspect explicit context or propose a new human approval. The previous workspace is not forced onto that decision. No active CLI turn or frozen approval is rewritten.

Slash commands preserve their ephemeral privacy. A private immutable destination receipt binds the verified workspace, channel and requester to the actual frozen approval hash. Completion delivery revalidates that receipt, the retained run identity and the bot's workspace before posting an ephemeral response. Routing metadata alone cannot authorize delivery, including after approval history is pruned. A per-effect claim precedes the Slack write; an uncertain outcome is not blindly repeated. Destination authorization lasts seven days. Slack membership, credentials and actual ephemeral delivery still require live acceptance.

## Verification and live acceptance

Required local gates are `pnpm typecheck`, `pnpm lint`, `pnpm test`, and `pnpm build`. Deployment configuration drift is checked with `pnpm check:deploy`. The focused backend acceptance files are `test/ephemeral-sandbox.test.ts` and `test/child-dispatch.test.ts`, run from `apps/backend` with its existing Vitest configuration.

Meaningful failure coverage includes immutable artifact scope, empty and binary output, child timeout and tampering, forbidden nested facets, unauthorized Slack clicks, durable message recovery, action publication claims, replay cursors, stream takeover, navigation isolation, and stalled room RPCs. A real Chromium harness also checks xterm rendering, presence, diffs, specialists, reconnect ordering, session navigation, and a narrow viewport using synthetic server frames.

No merge or production deployment is included. Live sandbox and R2 export, provider execution, Slack scope installation and button delivery, and process transport recovery require an authorized cloud environment. Baseline deployment run `41679318599` failed during Alchemy planning on Cloudflare authentication and rate limits after the build passed.
