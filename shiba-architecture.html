Shiba employee-platform architecture

Shiba is an approval-first AI employee workspace. One control plane coordinates people, employees, goals, approvals, execution lanes, evidence, and publication. Repository coding is one lane, not the product center.

Compatibility labels

The architecture role is Employee Orchestrator; the live implementation binding is still CodingOrchestrator. The sandbox child role is Run Execution Agent; the live implementation binding is still OpenCodeAgent. Documentation does not rename live Durable Object bindings.

Control plane

Employee Orchestrator

Conversation, employee/profile version, goal/plan/task interpretation, delegation, approval queue, and run lineage.

Authority plane

Workspace roles, exact grants, resource bindings, employee tool policy, frozen approval scope, expiry, and publication authority.

Run and event spine

Run/attempt lineage, progress, retries, cancellation, receipts, parent/child work, and outcome-unknown states.

State plane

Durable Objects coordinate live state. D1 owns shared domain records. R2 owns artifacts. KV, Vectorize, Queues, and Workflows have separate jobs.

Execution lanes

Repository sandbox

Ephemeral container, one selected harness, scoped repository access, diff/files/tests.

Artifact workspace

No-repository output workspace, private files, versions, provenance, expected deliverables.

Employee app actions

Policy-checked integration tools, exact action/input, receipts and idempotency.

Paired local machine

LocalDispatch mailbox, operator daemon, same result shape, machine-local evidence.

Browser and computer

Approved browser profile/session or dedicated computer, transcripts, screenshots, release state.

↓
Evidence and publication

Deliverables and review

Files, diffs, reports, drafts, logs, receipts, provenance, verification, caveats, or explicit unknown outcome. Humans review the evidence before follow-up.

Separate publication approval

Sending, posting, merging, publishing, purchasing, inviting, deleting, or mutating an external system requires its own approval and receipt.

State ownership

  • Durable Objects coordinate conversations, runs, sessions, dispatch, mailboxes, and realtime state.
  • D1 owns durable shared workspace and domain records.
  • R2 owns private artifact bytes and output archives.
  • KV owns small lookup state. Vectorize owns embeddings.
  • Queues and Workflows carry asynchronous control. They are not authority by themselves.

Current boundaries

  • Harnesses are execution CLIs or transports inside a lane.
  • Connected-app execution is not production-proven merely because its schema exists.
  • Employee-to-employee execution remains gated until its production contract passes.
  • A successful repository run does not prove artifact, local, browser, computer, or app-action lanes.
