title: Approvals and control
description: Choose what your AI employees can use, approve concrete actions, and review the output.
---

Shiba separates an employee's instructions, its access to tools, and permission to take an action. Giving an employee a role does not approve everything it might do.

## Before a workspace task runs

Repository and artifact-workspace runs wait for human approval. Read the card in the thread, or open **Approvals** to find pending decisions.

Check:

- **Outcome:** Is the task clear and limited to your brief?
- **Work target:** Is it the right repository and branch, or the intended artifact workspace?
- **Execution:** Are the model, account, and runtime the ones you expect?
- **Output:** Are the required files and checks appropriate?
- **Publication:** Is a pull request requested, and is a review included?

The card records the exact request. Approve it only if it matches your intent. If it does not, reject it and submit a revised brief.

## Approval is specific

Choosing **Approve** allows the request shown. It is not permission for every future task in the conversation. Choosing **Reject** prevents that proposed run from starting.

If your team uses Slack approvals, an authorized teammate can decide from the Slack card. Your administrator controls who can approve there.

## Publishing is a separate decision

For repository work, **Create pull request** requests publication after the work is ready. The initial run approval does not authorize the push or pull request.

Review the completed changes, then decide on the separate publication approval. That decision applies to the captured version of the changes. Merging follows its own review and approval process.

A document draft also does not automatically become a sent message or published campaign. Any supported external action must have the required account access and action approval.

## Connected apps have their own permissions

An account connection alone does not let every employee use it. Check the employee's **Tool policy**, granted resources, and any action approval card. Some narrowly scoped reads can use explicit standing consent where your installation supports it; that does not grant write or publishing access.

Installing a template, enabling a skill, or setting up an automation does not bypass these controls. See [Connections and tools](/docs/connections/).

## File reviews are another decision

In a deliverable card, **Approve** records that you accept the captured file. **Request revision** plus **Save review** records feedback. To run the revision, choose **Create revision approval**, then review and approve that new request. Neither accepting a file nor saving feedback sends it to an external service. See [Files and revisions](/docs/artifacts/).

## After approval

Read the result and its evidence. Approval gives permission to act; it does not guarantee that the output is correct or that an external service accepted the action.

Continue with [Threads and results](/docs/dashboard/) or [Pull request review](/docs/review/).
